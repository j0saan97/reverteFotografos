================================================================================
  GALERIA PRIVADA PARA FOTOGRAFOS - ESQUELETO DE ARQUITECTURA
  (referencia funcional: Oh My Photo / Pixpa / Pic-Time)
================================================================================

0. RESUMEN
--------------------------------------------------------------------------------
App web donde un FOTOGRAFO sube sesiones a galerias privadas y un CLIENTE
las ve (protegidas contra copia/captura), marca favoritas, envia seleccion
y descarga originales solo si el fotografo lo permite.

Arquitectura: SPA + BaaS (Supabase) + Object Storage (Cloudflare R2)
              + funciones serverless para la logica sensible.
Frontend organizado por FEATURES (vertical slices), con capas internas:
  ui -> hooks/estado -> servicios (api) -> cliente supabase / http
Backend "fino": la BD + RLS es la primera capa de seguridad; lo que no
se puede hacer con RLS va a Edge Functions (firmar URLs, procesar fotos).


1. STACK TECNOLOGICO
--------------------------------------------------------------------------------
FRONTEND
  - React 18 + TypeScript + Vite
  - React Router (rutas por rol)
  - TanStack Query (cache de datos del servidor)
  - Zustand (estado UI ligero: lightbox, seleccion, upload queue)
  - Tailwind CSS + componentes propios (o shadcn/ui)
  - React Hook Form + Zod (formularios y validacion compartida)
  - Uppy o react-dropzone (subida masiva con progreso)
  - PhotoSwipe / yet-another-react-lightbox (visor)

BACKEND / BAAS
  - Supabase:
      * Postgres (datos)
      * Auth (email+password, magic link) -> roles fotografo/cliente
      * Row Level Security (aislamiento por usuario/galeria)
      * Edge Functions (Deno/TS) -> logica que necesita secretos
  - Cloudflare R2 (S3-compatible, sin coste de salida)
      * bucket "originals"  -> PRIVADO, solo URLs firmadas
      * bucket "previews"   -> servido via Worker/CDN con token
  - Procesado de imagen:
      * Opcion A: Cloudflare Worker + Images (resize + watermark)
      * Opcion B: worker Node pequeno (Railway/Fly) con `sharp`
        escuchando una cola (tabla jobs o Supabase Queues)

INFRA / DEPLOY
  - Front: Vercel / Netlify / Cloudflare Pages (o estatico en Banahosting)
  - Dominios: app.tudominio.com (fotografo), tudominio.com/g/:slug (cliente)
  - Emails transaccionales: Resend (invitaciones, seleccion enviada)
  - Monitorizacion: Sentry (front + functions)

TOOLING
  - pnpm workspaces (monorepo)
  - ESLint + Prettier, Vitest + Testing Library, Playwright (e2e)
  - Supabase CLI (migraciones SQL versionadas, tipos TS generados)
  - GitHub Actions (lint, test, deploy migraciones)

4. CAPA DE APLICACION / LOGICA (Edge Functions)
--------------------------------------------------------------------------------
Todo lo que requiere SECRETOS o PERMISOS ELEVADOS va aqui, nunca en el front.

  sign-upload       IN: gallery_id, filename, mime, size
                    CHECK: el usuario es dueno de la galeria, cuota, tipo
                    OUT: URL PUT prefirmada a R2 (5 min) + photo_id
                    -> inserta fila photos(status='uploading')

  process-photo     Disparado al terminar la subida (o webhook R2)
                    -> genera: thumb (400px), preview (1600px + watermark)
                    -> actualiza photos(status='ready', width, height, keys)

  sign-view         IN: gallery_id
                    CHECK: acceso del cliente (RLS / PIN validado)
                    OUT: token corto para servir previews via Worker

  sign-download     IN: photo_id[]
                    CHECK: gallery.allow_download && acceso
                    OUT: URLs firmadas a originales (60 s) o ZIP
                    -> registra en downloads (auditoria)

  invite-client     IN: gallery_id, email
                    -> crea gallery_access + envia email con link

  submit-selection  IN: gallery_id
                    -> marca selection.submitted_at, bloquea cambios,
                       email al fotografo

  claim-photographer IN: code
                    CHECK: usuario autenticado + code == PHOTOGRAPHER_INVITE_CODE
                    -> profiles.role = 'photographer' (service role)

  contact           IN: name, email, phone?, sessionType, eventDate?, message
                    CHECK: contactSchema + honeypot anti-bots
                    -> inserta contact_requests + email al estudio (Resend)


5. CAPA DE DATOS (Supabase Postgres)
--------------------------------------------------------------------------------
profiles
  id (uuid, = auth.users.id) PK
  role            text  ('photographer' | 'client')
  display_name    text
  brand_name      text null          # solo fotografos
  brand_logo_key  text null
  created_at      timestamptz

galleries
  id              uuid PK
  photographer_id uuid FK -> profiles
  title           text
  slug            text UNIQUE         # /g/:slug
  pin_hash        text null           # acceso por PIN opcional
  cover_photo_id  uuid null
  allow_download  bool default false
  allow_selection bool default true
  max_selection   int null            # ej. "elige 30 fotos"
  watermark_text  text null
  expires_at      timestamptz null
  status          text ('draft'|'published'|'archived')
  created_at      timestamptz

gallery_access                        # que clientes ven que galeria
  gallery_id      uuid FK
  client_id       uuid FK -> profiles null
  email           text                # invitacion antes de registrarse
  invited_at, accepted_at
  PK (gallery_id, email)

photos
  id              uuid PK
  gallery_id      uuid FK
  original_key    text                # bucket privado
  preview_key     text                # con marca de agua
  thumb_key       text
  width, height   int
  size_bytes      bigint
  position        int                 # orden manual
  status          text ('uploading'|'processing'|'ready'|'error')
  created_at

selections
  id              uuid PK
  gallery_id      uuid FK
  client_id       uuid FK
  submitted_at    timestamptz null
  UNIQUE (gallery_id, client_id)

selection_items
  selection_id    uuid FK
  photo_id        uuid FK
  comment         text null
  PK (selection_id, photo_id)

  # selections ademas lleva:
  #   client_note   text null        # mensaje general al enviar la seleccion
  #   reopened_at   timestamptz null # el fotografo puede reabrirla

gallery_messages                      # dudas / conversacion cliente <-> fotografo
  id              uuid PK
  gallery_id      uuid FK
  photo_id        uuid FK null        # null = duda general de la galeria
  author_id       uuid FK -> profiles
  body            text
  read_at         timestamptz null
  created_at      timestamptz

downloads (auditoria)
  id, photo_id, client_id, created_at, ip

contact_requests                      # formulario de la web publica
  id, name, email, phone, session_type, event_date, message,
  handled bool, created_at

RLS (resumen):
  - profiles:        cada uno lee/edita el suyo
  - galleries:       fotografo -> CRUD de las suyas
                     cliente   -> SELECT si existe gallery_access aceptado
                                  y status='published' y no expirada
  - photos:          mismas reglas que su galeria; el cliente NUNCA ve
                     original_key (usar VIEW photos_public sin esa columna)
  - selections/items:cliente -> las suyas y solo si submitted_at is null
                     fotografo -> lectura de las de sus galerias
  - downloads:       solo insert via function (service role)
  - gallery_messages:cliente y fotografo de esa galeria leen/escriben;
                     nadie edita mensajes ajenos
  - contact_requests:solo insert via function (service role);
                     fotografos leen y marcan `handled`


6. CAPA DE ALMACENAMIENTO (R2)
--------------------------------------------------------------------------------
originals/{photographer_id}/{gallery_id}/{photo_id}.{ext}   PRIVADO
previews/{gallery_id}/{photo_id}.webp                       via Worker+token
thumbs/{gallery_id}/{photo_id}.webp                         via Worker+token
branding/{photographer_id}/logo.png                         publico

Flujo de subida:
  1. Front pide sign-upload           -> recibe URL PUT
  2. Front sube DIRECTO a R2           (no pasa por ningun servidor propio)
  3. Front avisa / webhook -> process-photo genera derivados
  4. Realtime de Supabase notifica status='ready' -> aparece en el grid

Flujo de visualizacion (cliente):
  1. Cliente entra -> sign-view -> token corto (ej. 15 min)
  2. <img src="https://img.tudominio.com/previews/...?t=TOKEN">
  3. El Worker valida token y sirve; sin token -> 403
  => no hay URL permanente que copiar y compartir


7. ANTI-CAPTURA / PROTECCION (vista de fotos del cliente)
--------------------------------------------------------------------------------
Premisa: NO se puede impedir al 100% (camara del movil, capturas del SO).
Objetivo: que lo que se capture NO tenga valor + disuadir.

Nivel servidor (lo que de verdad protege):
  - El cliente solo recibe PREVIEWS: max 1600px, webp calidad media
  - Marca de agua quemada en la imagen (nunca solo CSS)
  - Opcional: marca semi-invisible con email/id del cliente (trazabilidad)
  - URLs con token caducado; originales solo via sign-download

Nivel cliente (disuasion), en shared/protection:
  - Bloquear contextmenu, dragstart, selectstart sobre las imagenes
  - Overlay transparente encima del <img> (el clic no llega a la imagen)
  - Alternativa: pintar la foto en <canvas> en vez de <img>
  - user-select:none; -webkit-touch-callout:none (iOS mantener pulsado)
  - visibilitychange / window blur -> difuminar galeria (frena recortes
    y herramientas de captura que quitan el foco)
  - keyup 'PrintScreen' -> ocultar momentaneamente + limpiar portapapeles
    (solo funciona en algunos navegadores; es disuasorio)
  - @media print { .gallery { display:none } }
  - Bloquear Ctrl+S / Ctrl+P / Ctrl+Shift+S en la vista
  - Aviso visible: "Imagenes protegidas - (c) Nombre fotografo"


7b. SELECCION DE FOTOS Y COMENTARIOS (flujo del cliente)
--------------------------------------------------------------------------------
En cada card del grid (PhotoGrid -> PhotoCard):
  - Checkbox/corazon en esquina superior (siempre visible en movil,
    al hover en desktop). Click en la foto = abrir lightbox; click en el
    check = marcar/desmarcar (no abre el visor).
  - Icono de bocadillo -> comentario sobre ESA foto
    (ej. "quitar granito", "esta en blanco y negro")
  - Badge si la foto ya tiene comentario
  - En el lightbox: mismo check + comentario + teclas (F = marcar, flechas)

Barra fija inferior (SelectionBar):
  - "12 / 30 seleccionadas" (respeta galleries.max_selection)
  - Filtro: Todas | Seleccionadas | Con comentario
  - Boton "Revisar y enviar"

Pantalla "Revisar y enviar" (/my/:slug/selection):
  - Miniaturas de las seleccionadas con su comentario editable
  - Textarea "Mensaje para el fotografo" -> selections.client_note
  - Confirmar -> submit-selection:
       * guarda submitted_at, bloquea cambios (RLS)
       * email + notificacion al fotografo
       * el cliente ve "Seleccion enviada el dd/mm" (solo lectura)

Guardado: cada check/comentario se guarda al momento (optimistic update
con TanStack Query), asi el cliente puede dejarlo a medias y volver.

Dudas generales (pestaña/boton "Mensajes" en la galeria):
  - Hilo simple cliente <-> fotografo en gallery_messages (photo_id null)
  - Supabase Realtime para que aparezcan al instante
  - Contador de no leidos para ambos

Lado fotografo (/galleries/:id/selection):
  - Lista de clientes con estado: pendiente / enviada
  - Grid filtrado con las elegidas + comentarios por foto
  - Mensaje general del cliente
  - Acciones: exportar lista de nombres de archivo (CSV / copiar para
    filtrar en Lightroom), reabrir seleccion, responder mensajes

Componentes nuevos (features/selections):
  PhotoCard, SelectCheckbox, PhotoCommentPopover, SelectionBar,
  SelectionReviewPage, MessagesPanel, useSelection, useMessages


8. SEGURIDAD GENERAL
--------------------------------------------------------------------------------
  - Service role key SOLO en Edge Functions, nunca en el front
  - Validacion con Zod en front Y en functions (packages/shared)
  - PIN de galeria: hash (bcrypt) + rate limit de intentos
  - Limites: tipos (jpg, png, heic, webp), tamano maximo por foto, cuota
    de almacenamiento por fotografo
  - Expiracion de galerias aplicada en RLS, no solo en UI
  - CORS restringido al dominio de la app
